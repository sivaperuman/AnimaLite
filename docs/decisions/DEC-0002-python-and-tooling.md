# DEC-0002 — Python baseline, dependencies and tooling

* **Status:** Accepted
* **Deciding role:** implementation
* **Affects:** requirements §6.2, handoff v0.2 §2 (Python/tooling), §8 (CI cost)

## Decision

* **Python:** `requires-python = ">=3.11,<3.14"`. The pinned development and CI
  baseline is **CPython 3.11** (3.11.15 verified). §6.2 says "Python 3.11+"; 3.11
  is the lowest supported minor, so building and testing against it is what makes
  the floor real.
* **Runtime dependencies:** `pydantic>=2.9,<3` and `numpy>=1.26,<3`. Nothing else.
* **Development dependencies:** `pytest`, `ruff` (linter *and* formatter), `mypy`.
* **Lock:** `constraints/dev-linux-cpython311.txt`, generated by
  `tools/write_constraints.py` from a `pip install --report` resolution. It pins
  exact versions and records each artifact's sha256 as a comment, so it works
  both as a `-c` constraints file and as a record of what was tested.
* **Build backend:** hatchling, src layout, `py.typed` shipped.

## Why these dependencies

The requirement is "typed, versioned schemas" where "unknown critical fields must
not be silently ignored". Pydantic v2 gives that directly: `extra="forbid"` turns
an unrecognised key into an error, model validators express cross-field
invariants (a profile cannot claim qualification eligibility without a learned
component), and JSON round-tripping is the storage format anyway.

NumPy carries frame buffers. A 640×360 RGB frame is 691 200 bytes and there are
72 of them per clip; pure-Python buffer arithmetic would dominate the very timings
the harness exists to measure.

FastAPI, SQLite, Redis and PostgreSQL are all named in §6.2 but are **not**
dependencies here: handoff §2 says no service fleet, database or web UI is needed
for the first CPU proof, and adding SQLite solely for a timing experiment is
called out as the wrong move.

Ruff, mypy and pytest are the recommended defaults in handoff §2. Ruff also
replaces a separate formatter, which keeps CI to one tool for lint and format.

## Why a constraints file rather than a hash-locked requirements file

`--require-hashes` forces every dependency to be listed with hashes and disables
resolution, which makes editable installs and platform variation awkward at this
stage. The constraints file pins exact versions (so a resolution drift is
visible) and records the hashes as comments (so the artifacts are identifiable),
while `pyproject.toml` ranges stay authoritative. Moving to enforced hash pinning
is a one-file change if review prefers it.

## Reversal

All of it is reversible: change the ranges in `pyproject.toml`, regenerate the
lock with `tools/write_constraints.py`, and re-run the documented checks.
